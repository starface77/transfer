# ЗАДАЧА ДЛЯ DEVIN: Построить Sharrowkin — автономный ИИ-агент для разработчиков

## Что это
Sharrowkin — локальный автономный ИИ-агент (аналог Google Jules), который получает задачу от разработчика, сам читает код проекта, сам пишет патчи, сам запускает тесты и сам исправляет ошибки в цикле, пока задача не решена. Всё работает локально, без облака, zero-telemetry.

## Что уже есть в репозитории (фундамент)

### 1. sharoukin_desktop/src/agent.py
Ядро когнитивного цикла агента. Реализован 5-фазный цикл:
- Observe (сканирование файлов проекта)
- Recall (поиск аналогичных решений в памяти)
- Reason (генерация кода через LLM)
- Stabilize (запуск тестов, проверка результата)
- Commit (фиксация изменений)

Сейчас шаги симулированы через time.sleep. Нужно сделать их реальными.

### 2. sharoukin_desktop/src/app.py
GUI-прототип на Tkinter в стиле Google Jules: слева чек-лист плана + лог мыслей, справа diff-viewer с подсветкой синтаксиса. Это референс по структуре интерфейса — его нужно переписать на веб (React/Next.js + FastAPI бэкенд).

### 3. lazystandup/
Готовый CLI-инструмент. Парсит AST-изменения кода из нашей кастомной системы контроля версий (s-git) и генерирует стендап-отчёты через LLM. Поддерживает движки: Gemini (REST API), OpenAI, Ollama, offline. Встроить как вкладку в веб-интерфейс.

## Ключевые научные открытия нашего R&D — ИСПОЛЬЗУЙ ИХ В АРХИТЕКТУРЕ АГЕНТА

За месяцы исследований мы открыли несколько мощных принципов, которые делают нашего агента уникальным. Это не абстрактная теория — это работающий код:

### Принцип 1: Recursive Latent DNA (RLD) — обучение агента на собственном опыте
Файл: lazystandup/../rld/src/rld/core.py (класс RecursiveLatentDNA, ~1000 строк)

Суть: каждый раз, когда агент успешно решает задачу, он сжимает весь ход решения (последовательность состояний, действий, инструментов, финальный ответ) в компактный "ген рассуждений" (ReasoningGene). Гены хранятся в памяти. Когда приходит новая задача, система ищет похожие гены через гибридный поиск (dense cosine similarity + sparse term overlap + success rate + stability score) и подмешивает их в контекст LLM.

Ключевой метод: `rld.active_context(query)` — возвращает RLDContext с текстом контекста, который нужно вставить в system prompt модели перед генерацией.

Ещё есть фаза "сна" (`rld.sleep()`) — офлайн-консолидация памяти: энтропийное затухание неиспользуемых генов, слияние похожих генов в "хромосомы", стабилизация часто используемых паттернов, ре-анкоринг эмбеддингов к центроиду. Это биологическая модель забывания и укрепления памяти.

КАК ИСПОЛЬЗОВАТЬ: После каждой успешно решённой задачи агент вызывает rld.observe() чтобы сохранить ген. Перед каждой новой задачей — rld.active_context() чтобы получить релевантный контекст из прошлого опыта. Периодически (раз в N задач) — rld.sleep() для оптимизации памяти.

### Принцип 2: Dynamic Segmented Memory (DSM) — структурированная долговременная память
Файл: modules/dsm/src/dsm/memory.py

Суть: гибридная векторно-графовая память. Каждый сегмент хранит текст + dense embedding + sparse TF-IDF index + граф связей с другими сегментами + категориальную иерархию. Поиск идёт одновременно по всем каналам и результаты объединяются.

КАК ИСПОЛЬЗОВАТЬ: Агент сохраняет в DSM свои знания о проекте (какие файлы за что отвечают, какие паттерны используются, какие баги уже чинились). При новой задаче — семантический поиск по DSM даёт агенту "институциональную память" о проекте.

### Принцип 3: AST-уровневое понимание кода (s-git)
Файл: lazystandup/../semanticgit/src/sgit/

Суть: вместо текстовых диффов мы парсим Python-файлы в Abstract Syntax Tree и отслеживаем изменения на уровне классов, методов и сигнатур функций. Это даёт агенту структурное понимание кода, а не просто "строка 42 изменилась".

КАК ИСПОЛЬЗОВАТЬ: Когда агент анализирует проект, он должен использовать AST-парсер (стандартный Python ast модуль) чтобы понимать архитектуру: какие классы есть, какие методы, какие зависимости между файлами. Это в 10 раз эффективнее, чем скармливать модели весь исходный код целиком.

### Принцип 4: Когнитивный цикл свободной энергии (FieldScript)
Файл: testslang/fieldscript_v1.py (класс FieldScript)

Суть: агент работает по циклу минимизации "свободной энергии" (Free Energy Principle). На каждом шаге он:
1. Наблюдает текущее состояние (Observe)
2. Извлекает релевантные знания из памяти (Recall)
3. Генерирует предсказание/решение в латентном пространстве (Reason)
4. Проверяет расхождение предсказания с реальностью — "энергию ошибки" (Stabilize)
5. Если энергия низкая — решение стабильно, фиксируем. Если высокая — цикл повторяется.

КАК ИСПОЛЬЗОВАТЬ: Это главный паттерн работы агента. Не просто "сгенерируй код и всё". А именно: сгенерируй → проверь тестами → если тесты упали, энергия высокая → перегенерируй с учётом ошибки → повтори до стабильности.

## Что нужно построить

### Фаза 1: Веб-интерфейс (UI в браузере)
Сделай веб-приложение на React/Next.js + Python FastAPI бэкенд. Дизайн как у Google Jules — минималистичный, тёмная тема, два столбца:

Левая панель:
- Чек-лист шагов когнитивного плана (Observe, Recall, Reason, Stabilize, Commit) с живыми статусами (ожидание → в процессе → готово)
- Под чек-листом — терминал мыслей агента (лог его рассуждений в реальном времени через WebSocket)

Правая панель:
- Diff-viewer с подсветкой синтаксиса (добавленные строки зелёные, удалённые красные, заголовки фиолетовые)
- Кнопки Accept/Reject для предложенных изменений

Верхняя панель:
- Поле ввода задачи (prompt bar)
- Путь к проекту (workspace path)
- Кнопка запуска
- Индикатор статуса агента

Нижняя панель:
- Вкладка "Standup Report" — интегрировать lazystandup, показывать сгенерированный отчёт

### Фаза 2: Реальный агентный бэкенд
Сделай agent.py реальным:
1. Чтение файлов проекта через os/pathlib
2. AST-парсинг через стандартный Python ast модуль для структурного понимания кода
3. Подключение к Google Gemini API (env: GEMINI_API_KEY) для генерации кода — используй REST API напрямую (POST на https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent?key=KEY)
4. Запись сгенерированных патчей в файлы
5. Запуск pytest через subprocess и парсинг stdout/stderr
6. Self-healing loop: если тест упал → отправить traceback обратно в LLM → перегенерировать → повторить (макс 3 итерации)
7. После успешного решения — сохранить опыт как "ген" в RLD-памяти

### Приоритеты
1. Скорость разработки — сначала работающий функционал, потом полировка
2. Веб-интерфейс в браузере (не десктоп)
3. Реальное подключение к Gemini API
4. Self-healing loop (тесты → фикс → тесты)
5. Интеграция RLD памяти для обучения на собственном опыте
